Evaluation project

Tracebench A benchmark for on-call AI agents

I built a small online shop with three services and a real git history, then set up six incidents in it. Each one fires a page. Three low-cost AI models took the pages. They read the logs, traces and code, decided what to do and wrote the fix. Every fix was then checked by tests the model never saw and by replaying the same traffic.

The surprise

Six correct fixes failed on formatting

Git refused six of the models' fixes. Five were for the c1 leak and one was Haiku's fix for c3. The code in each was right. All six were rejected before any test ran.

The incidents

Six ways to break a shop

Every bad commit passes the shop's own tests, as a real one would pass CI. Two incidents need no code change at all.

  • c1 · Connection leak

    fix

    A refactor stops returning the database connection when an item is out of stock. The pool fills and checkout fails.

  • c2 · Wrong limit

    fix

    A change to slow down stock bots limits checkouts per product instead of per user. Buyers of popular products get errors.

  • c3 · Decoy deploy

    fix

    A new two-item cap in orders throws a server error. A harmless web deploy follows 90 seconds later.

  • c4 · Slow query

    fix

    Case-insensitive product lookups scan all 6,000 rows, so product pages time out.

  • c5 · Outside lock

    escalate

    A job outside the shop holds a database lock. Nothing in the code is wrong; the right call is to hand it on.

  • c6 · Load test

    dismiss

    A planned load test hits the rate limit and is over before the page. Customers were never affected.

What I learned

Finding the cause is easier than shipping the fix

Diagnosis is strong

Haiku found the right service, commit and place in the code in all 8 incidents that needed a fix, Luna in 7. In two of them the place is a setting, not a function. No model fell for the decoy deploy, which the prompt had warned about.

Fixes fail for small reasons

Diff formatting cost six correct fixes. The slow query (c4) was the one real coding miss. Haiku's and Luna's c4 fixes passed the shop's tests but failed the hidden lookup checks.

Knowing when not to fix differs

Haiku escalated the outside lock both times. Luna dismissed the load test both times but tried to patch the lock. Neither rule ever dismisses.

Reliability matters as much as skill

DeepSeek Flash wrote the most valid fixes when it answered, but lost 6 of 12 incidents to broken or cut-off answers. It also cost the most.

How the grading stays honest

The model never grades its own work

  1. 1

    Investigate in a sandbox

    The investigation runs as a separate account with no keys and no internet. Its only connection is a local broker that holds the keys, records every call and stops at a spending cap.

  2. 2

    Rebuild from the record

    A second, untouched copy of the code replays the broker's record. Its report must match the first one byte for byte, or the run counts as invalid.

  3. 3

    Check every fix outside the model's reach

    Each fix is applied to the exact commit that was running, then the shop's tests, hidden tests and a full traffic replay run in the sandbox. The answers never leave this side.

  4. 4

    Spend only what I approved

    Every paid run needs a signed budget that I approve with Touch ID. Any change to the grading code voids it.

Limits

What this does not show

Small numbers

One run of 12 incidents. A difference of one incident between models is noise.

A simulated shop

The shop runs on a simulated clock with an in-memory SQLite database. It is an application-level demo. The two rules read every event and all the code, and their thresholds were tuned on this simulator.

Limited retries

A model gets a second chance after a broken answer, but two broken answers in a row end the incident. An answer cut off at the length limit ends it straight away. The same rules applied to every model, and they hurt DeepSeek Flash most.

Patches still need a person

Fixed code runs in the same process as its checks. The sandbox keeps a hostile fix away from files, keys and the network, and a person reviews every patch before it would ship.
